## Why this minimal index is justified

The primary key already supports selection-only importer ledger reads, and the work index supports work-only checks. Neither is a single covering B-tree for the pair lookup associated with checking referencing rows during parent member changes. PostgreSQL can combine the existing indexes (the synthetic baseline actually uses BitmapAnd), but this is not the same as the requested pair access path. Leading `selection_slug`, then `work_id`, supports selection-local pair lookups without changing uniqueness or data semantics. [PostgreSQL multicolumn indexes](https://www.postgresql.org/docs/17/indexes-multicolumn.html).

Importer prior-record lookup is selection-only; Work creation/identity matching is unaffected. Browse and Search both use `loadEditorialCatalog` → public `catalog_editorial_page` → persistent selection/category tables. They do NOT read the private ledger directly. This is a foreign-key/admin lookup fix, not a claim of faster Browse/Search rendering.

Current production editorial volume is zero. Planned importer volume is 974 members/ledger rows in one selection. Stress testing 100 selections × 1000 Works is an access-path demonstration, not a production forecast. With one selection and selective Work IDs the existing work index may already be fast. The extra index adds storage and write-maintenance costs. No unique, partial, INCLUDE or additional speculative indexes are needed. Empty table permits a regular transactional CREATE INDEX; no CONCURRENTLY.
